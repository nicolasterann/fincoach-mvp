## 1. Alcance implementado frente al contrato 2B

### 1.1 Cascada — captura ordinaria ajena a una propuesta pendiente

Se añadió `loopPendingManifestActionRelated`, una decisión pura y mecánica que limita el camino `reject → restage → successor` a una de estas dos relaciones:

1. la capability nueva ya existe en el manifiesto; o
2. la entidad objetivo tipada de la acción nueva coincide con una entidad objetivo del manifiesto después de canonicalizar nombre↔id contra el catálogo durable.

Montos, fechas, cuentas fuente y texto del usuario no participan. En particular, `log_movement` no toma su cuenta fuente como identidad objetivo: un taxi desde Pichincha no se vuelve parte de una propuesta pendiente de `create_account` ni siquiera porque ambas acciones convivan en la misma conversación.

La condición corre **antes** de reclamar, rechazar o reconstruir el manifiesto. Si no hay relación, la mutación obtiene una operación fresca y sigue el camino ordinario. La consolidación histórica de acciones relacionadas queda intacta: misma capability sigue extendiendo/reemplazando; pago y cierre sobre la misma deuda tipada siguen formando un sucesor.

Resultado black-box del rojo heredado:

- antes: café `3 USD` escrito; taxi `4 USD` absorbido; manifiesto `create_account` rechazado y sucesor `create_account + log_movement` propuesto;
- después: café `3 USD` y taxi `4 USD` escritos exactamente; el manifiesto original de `create_account` conserva id, hash, payload y status `proposed`; la captura posterior no crea manifiesto ni pregunta.

### 1.2 Monto compacto — gramática cerrada de valores

La frontera compartida `statedAmounts` reconoce dos sufijos numéricos exactos, con o sin espacio:

~~~text
<número> mil  → número × 1.000
<número> k    → número × 1.000
~~~

El número base conserva la normalización LatAm existente. Por eso:

~~~text
50mil  = 50000
50 mil = 50000
1,5k   = 1500
~~~

La gramática no selecciona capability, entidad, dirección ni moneda. Sólo transforma un token numérico ya encontrado. Un sufijo fuera del conjunto —por ejemplo `50m`— no gana escala ni autoridad sobre `50000`; conserva el comportamiento previo del número base. Los filtros existentes de fechas, porcentajes, identificadores y conteos siguen corriendo sobre el token.

Resultado black-box del rojo heredado:

- antes: `Coto 50mil desde Supervielle` dejaba cero filas y un manifiesto `log_movement(50000)` pendiente;
- después: una expense exacta de `50000 ARS`, balance exacto, un turno, cero manifiestos, cero confirmaciones y cero repreguntas.

## 3. Decisiones de diseño

### 3.1 Relación por capability **o** entidad objetivo

El contrato autoriza ambas identidades. La misma capability es una relación suficiente aunque cambie la entidad, porque esa es la forma histórica de extender un conjunto homogéneo. Entre capabilities distintas se exige igualdad de target tipado canonicalizado. Esto conserva `pagar tarjeta → cerrar esa tarjeta` y excluye `create_account → registrar taxi`.

Se reutilizó `loopActionEntityTargetKey`; no se creó una segunda ontología. Se elimina únicamente el prefijo de capability para comparar la misma clase/clave objetivo entre tools. Las cuentas fuente permanecen fuera porque el helper histórico las define como argumentos mutables, no como target.

### 3.2 Escala en el productor común, no en el loop

El fix vive en `amount-evidence.ts`, de modo que planner, guard, executors y publicación consumen la misma cifra canónica. Añadir una excepción `50mil` en el dispatcher habría sido routing semántico duplicado y habría dejado las demás fronteras en desacuerdo.

### 3.3 Forma no reconocida

El matcher se detiene antes del sufijo desconocido y conserva el número base heredado. Así `50m` no se convierte en `50000`; el guard continúa pidiendo/proponiendo cuando el modelo intenta escribir `50000`. No se añadió diccionario de expresiones ni inferencia de moneda.

### 3.4 Release permanente

El comando npm no reemplaza los comandos auditables individuales. Es un fail-fast de release; en esta entrega sus dos componentes se ejecutaron por separado para conservar salidas y exit codes directos.

## 6. Riesgos y objeciones

### 6.1 Cobertura de identidad objetivo

La relación cross-capability depende deliberadamente de `loopActionEntityTargetKey`, la ontología ya usada para reemplazo vivo. Una capability futura que necesite consolidación cross-capability debe declarar un target allí o quedará como no relacionada; el lado seguro será ejecutar/rehusar según sus propias barreras en una operación fresca, no absorber silenciosamente. IR345a fija las relaciones actuales, pero no puede anticipar una entidad nueva.

### 6.2 Misma capability es relación amplia

Dos acciones de la misma capability sobre entidades distintas se consideran relacionadas, tal como exige la rama «entidad/capability» del contrato y como funcionaba la consolidación de lotes homogéneos. Esto mantiene pagos múltiples y correcciones. Si Claude pretendía exigir además igualdad de entidad cuando ambas actions tienen target, eso sería una política más estrecha que A41-3.1 y cambiaría escenarios históricos; no la inferí unilateralmente.

### 6.3 Gramática compacta

`mil|k` escala cualquier token numérico válido antes de que corran los filtros existentes. No interpreta moneda. Una forma fuera del conjunto no obtiene la escala, pero el número base puede seguir siendo evidencia exactamente como antes. El caso `50m` demuestra que nunca prueba `50000`.
